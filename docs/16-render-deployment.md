# Deploy the combined app as one Render Web Service

The React production build goes into ignored `backend/public/`; the Express server serves that folder, `/api/v1` and `/media` on the same origin. Use Render's **New → Web Service** form. No Blueprint or separate frontend service is needed. Neon continues to hold PostgreSQL data and product images. The Dockerfile at the repository root builds both workspaces.

## Select these options in Render

| Field | Selection |
| --- | --- |
| Source | Connect the private GitHub repository `touhid404/furniture-commerce` |
| Language | **Docker** |
| Branch | `main` |
| Region | **Ohio (US East)** if available, near the Neon us-east-2 branch |
| Root Directory | **Leave blank**; do not enter `backend/` |
| Dockerfile Path | `./Dockerfile` (default) |
| Docker Build Context | `.` (repository root, default) |
| Instance Type | **Free** for a preview; review the Free limitations below |
| Health Check Path | `/api/v1/health/ready` |

The image starts Express on `0.0.0.0:$PORT` and includes the compiled React assets. No build or start command is required with Docker. Do not upload `backend/public/` manually; Render builds it from GitHub. Do not run `db:reset`, `seed`, or schema pushes during deployment. Run only reviewed forward migrations separately with the correct Neon branch before a release that needs them.

## Environment variables

Enter these in the Web Service's **Environment** section, never in GitHub or frontend variables. Get the database and object-storage values from the same Neon `production` branch. For `PUBLIC_APP_URL`, use the exact assigned Render HTTPS URL after the service name is known; update and redeploy if you add a custom domain.

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `STORE_CONFIG_PATH` | `config/stores/production.json` |
| `NEON_BRANCH` | `production` |
| `DEMO_SEED` | `false` |
| `PUBLIC_APP_URL` | Exact `https://...onrender.com` origin or reviewed custom HTTPS origin |
| `DATABASE_URL` | Neon pooled PostgreSQL URL |
| `SESSION_SECRET` | Long random secret, stable across deployments |
| `MFA_ENCRYPTION_KEY` | Stable 64-character hexadecimal encryption key |
| `AWS_ENDPOINT_URL_S3`, `AWS_REGION` | Neon production object-storage endpoint and region |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Neon production object-storage credentials |
| `STORAGE_BUCKET` | `assets` |
| `RUN_WORKER_IN_WEB` | `true` to process email and media-deletion outbox jobs while the web service runs |

For email, add `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD` and `SMTP_FROM` only after selecting a working provider. Render Free Web Services block outbound ports 25, 465 and 587; use a provider-supported allowed port, such as 2525, and verify delivery. Without working SMTP, messages remain queued and account email flows cannot be considered ready. `DATABASE_URL_UNPOOLED` is needed only for reviewed migration commands outside this runtime.

## Before real orders

`config/stores/production.json` disables demo access, but still contains sample ELNAVO branding, `support@example.com`, illustrative products and US/USD rules. Set actual merchant identity, support email, price books, tax, shipping and policies. Put `ADMIN_EMAIL=admin@ex.com`, `ADMIN_USERNAME=admin` and a unique strong `ADMIN_PASSWORD` in the ignored root `.env.local` (or in private Render environment variables for an explicit Render-shell provisioning run). Run `npm run admin:create` once with access to the production database, then enroll MFA. The command stores an Argon2 hash; the password is not needed by the web process after provisioning. Production middleware rejects the old weak testing account.

After deployment, verify `/api/v1/health/live` and `/api/v1/health/ready` return 200, `/` and `/shop` load their `/assets/` files, `/api/v1/config` reports `demo: false`, a published product image resolves through `/media`, and a controlled sign-in/checkout works. Test the outbox with actual email delivery before promising notifications. If browser writes report an origin error, check that `PUBLIC_APP_URL` exactly matches the address in the browser.

## Free service limits

The embedded worker and the npm `node-cron` health check run only while the Web Service process is running. In production, the job requests `${PUBLIC_APP_URL}/api/v1/health/live` on the `*/14 * * * *` schedule and logs the result. It cannot wake the app after Render stops or restarts it. Render Free spins a service down after 15 minutes without **inbound** traffic. A request generated by the same service is not a reliable way to keep it awake, so this job does not guarantee continuous uptime. During sleep, queued jobs wait and the next visitor may see a cold start. Neon stores the durable orders, outbox and images, so they survive restarts. Render Free also has monthly usage limits and may restrict high outbound traffic to Neon. A paid always-on Web Service is required for predictable availability without an external monitor; a separate worker is appropriate when timely email matters.
